# 아키텍처 설계 참조 자료 (ISO 26262 Part 6 / A-SPICE 4.1)

이 스킬은 아키텍처 산출물을 설계·검토할 때 지켜야 할 규칙과 체크리스트입니다.
아래 규칙을 모두 만족하지 못하는 아키텍처 초안은 미완성으로 취급하고, 어떤 항목이
빠졌는지 명시적으로 표시하세요.

## 0. 산출물 템플릿

이 프로젝트의 아키텍처 설계 산출물은 사용자가 제공하는 템플릿을 따라야 합니다.
템플릿 파일은 `D:\NGV\NGV\.claude\skills\architecture-design\templates\` 아래에
위치할 예정입니다 (예: `architecture-design-template.md`). **작업을 시작하기 전에
이 디렉터리에 템플릿 파일이 있는지 먼저 확인하세요.**

- 템플릿이 있으면: 그 템플릿의 항목/구조/표 형식을 그대로 따르고, 아래 1~8절의
  규칙은 템플릿의 각 항목을 채우는 기준으로 사용합니다.
- 템플릿이 아직 없으면: 사용자에게 아직 템플릿을 받지 못했다고 알리고, 아래 1~8절
  규칙만으로 구성한 임시 초안 구조(아키텍처 개요, 후보 비교, 컴포넌트 목록, 인터페이스
  명세, 동적 동작, 응집도/결합도 점검표, SOLID 점검표, 통합 순서, 추적 매트릭스)를
  사용해 초안을 작성하되, 템플릿 수신 후 재구성이 필요하다는 점을 명시하세요.

## 표·다이어그램 작성 형식 (공통 규칙)

- **표 우선**: 템플릿에 특정 항목의 서식이 정의되어 있지 않은 경우, 줄글
  (prose)로 풀어쓰지 말고 적절한 표를 구성해 그 안에 작성합니다. 사용자가
  한눈에 비교·스캔할 수 있는 형태를 우선합니다. 템플릿에 이미 표/서식이
  정의되어 있다면 그 형식을 그대로 따릅니다(0절 템플릿 확인 절차와 연계).
- **다이어그램은 렌더링된 이미지로 문서에 포함**: BDD/Component/Sequence
  Diagram 등 Mermaid/PlantUML 다이어그램 소스 코드를 문서 본문에 코드
  블록으로 직접 삽입하지 않습니다.
  1. 다이어그램 원본 소스는 별도 파일로 저장합니다(예:
     `diagrams/<컴포넌트ID 또는 시나리오명>.mmd` 또는 `.puml`).
  2. 그 소스를 이미지(PNG 또는 SVG)로 렌더링합니다(예: Mermaid CLI `mmdc`,
     PlantUML jar 등 프로젝트에서 사용 가능한 도구).
  3. 문서에는 렌더링된 이미지만 `![설명](이미지 경로)` 형태로 삽입하고,
     원본 소스 파일 경로를 캡션/각주로 함께 명시해 추적 가능하게 합니다.
  4. 원본 소스가 변경되면 이미지도 함께 재렌더링합니다 — 이미지와 소스가
     불일치한 채로 남겨두지 않습니다.
  5. 렌더링 도구를 실행할 수 없는 환경이라면, 그 사실을 산출물에 명시하고
     원본 소스 파일 경로만 남기되(코드 블록으로 본문에 삽입하지 않음),
     "렌더링 필요"로 표시합니다.

## 1. ISO 26262 Part 6 준수 (아키텍처 설계 원칙)

ISO 26262-6 Clause 7(소프트웨어 아키텍처 설계)의 원칙을 시스템/소프트웨어 아키텍처
전반에 적용합니다:

- **계층 구조**: 아키텍처는 최상위 구조에서 하위 요소로 분해되는 계층 구조를 가진다.
  임의로 평면적인 컴포넌트 나열을 하지 않는다.
- **컴포넌트 크기·복잡도 제한**: 하나의 컴포넌트가 과도하게 많은 책임/기능을 갖지
  않도록 크기와 복잡도를 제한한다 — 제한을 넘으면 분해(decompose)한다.
- **인터페이스 크기 제한**: 인터페이스의 오퍼레이션 수, 파라미터 수를 필요한
  범위로 제한하여 불필요한 결합을 만들지 않는다.
- **높은 응집도(High Cohesion)** — 하나의 컴포넌트 내부 요소는 하나의 명확한 책임을
  중심으로 강하게 연관되어야 한다. 판정 기준:
  | 응집도 유형 | 허용 여부 |
  |---|---|
  | 기능적(Functional), 정보적(Informational) | 목표 — 적극 채택 |
  | 순차적(Sequential), 통신적(Communicational) | 허용 |
  | 절차적(Procedural), 시간적(Temporal) | 지양 — 재검토 필요 |
  | 논리적(Logical), 우연적(Coincidental) | 금지 — 반드시 재설계 |
- **낮은 결합도(Low Coupling)** — 컴포넌트 간 의존은 필요한 최소한으로 제한한다.
  판정 기준:
  | 결합도 유형 | 허용 여부 |
  |---|---|
  | 데이터(Data), 스탬프(Stamp) | 목표 — 적극 채택 |
  | 제어(Control) | 지양 — 불가피할 때만, 사유 명시 |
  | 공통(Common/전역상태 공유), 내용(Content/내부 구현 직접 접근) | 금지 |
- **오류 검출/처리 메커니즘**: 안전 관련 컴포넌트에는 ASIL 등급에 맞는 오류 검출
  메커니즘(범위 검사, 타당성 검사, 워치독, 다양성 중복 등)과 오류 처리 메커니즘
  (안전 상태 전이, 재시도, 성능저하 운전 등)을 아키텍처 수준에서 명시한다.
- **ASIL 분리·간섭으로부터의 자유(Freedom from Interference)**: 서로 다른 ASIL을
  갖는 요소, 또는 ASIL과 QM 요소가 함께 통합될 때는 이들이 서로 의도치 않게
  간섭하지 않는다는 근거(공간/시간 분리, 인터페이스를 통한 통제된 상호작용 등)를
  아키텍처에 명시한다. 근거 없이 서로 다른 ASIL 요소를 동일 컴포넌트에 섞지 않는다.
- **표기법**: 아키텍처는 반드시 半정형(semi-formal) 이상의 표기법(Mermaid/PlantUML의
  Block Definition Diagram, Component Diagram, Sequence Diagram 등)으로 표현한다.
  ASIL이 높을수록(C/D) 半정형/정형 표기법 사용을 더 강하게 요구하며, 자연어 설명만
  있는 아키텍처는 미완성으로 취급한다.

## 2. A-SPICE 4.1 준수 (SYS.3 / SWE.2 정합성)

SYS.3(시스템 아키텍처 설계), SWE.2(소프트웨어 아키텍처 설계)의 기본관행에 따릅니다:

- 아키텍처를 개발하고, 요구사항을 아키텍처 요소에 할당한다 — 할당되지 않은
  요구사항, 요구사항 근거 없는 아키텍처 요소가 남지 않게 한다.
- 아키텍처 요소 간 **인터페이스**를 정의한다(4절 참고).
- 아키텍처 요소의 **동적 동작**(상호작용, 타이밍, 상태 전이)을 기술한다.
- 자원 사용 목표(메모리, CPU, 통신 대역 등)를 정의한다(해당 시).
- **대안 아키텍처를 평가**하고 선정 근거를 남긴다(6절 참고) — 단일안만 제시하고
  바로 확정하지 않는다.
- 정의된 평가 기준(모듈성, 시험용이성, 이해용이성, 자원 사용 등)에 따라 아키텍처를
  평가한 기록을 남긴다.
- 요구사항 ↔ 아키텍처 요소 간 **양방향 추적성**을 확보한다(8절 참고).
- 아키텍처 요소 간, 그리고 요구사항과의 **일관성**을 확보한다.
- CL2 수준의 산출물 관리 기준([[aspice-auditor]] 스킬 참고)에 맞게, 식별·버전·
  리뷰 증적·추적성을 갖춘 상태로 산출물을 만든다.

## 3. SOLID 원칙 적용

각 컴포넌트/모듈을 설계·검토할 때 아래 원칙을 하나씩 명시적으로 점검하고, 위반
사항이 있으면 산출물에 표시합니다(임베디드/정적 언어 환경에서는 함수 포인터,
전략 테이블, HAL 계층 등으로 구현될 수 있음을 감안하되 원칙 자체는 동일하게 적용):

- **단일 책임 원칙(SRP)**: 컴포넌트가 변경되어야 할 이유가 하나인지 확인한다.
  둘 이상의 서로 다른 이해관계자/사유로 변경될 수 있다면 분리한다.
- **개방-폐쇄 원칙(OCP)**: 새로운 변형(파생 변종, 옵션, 신규 하드웨어 등)을 추가할
  때 기존 컴포넌트의 내부 수정 없이 확장(신규 구현체 추가, 확장점 사용)으로 대응할
  수 있는지 확인한다.
- **리스코프 치환 원칙(LSP)**: 동일 인터페이스의 여러 구현체(예: 다른 하드웨어
  변형, 시뮬레이션/실장치)가 호출자 관점에서 치환 가능한 계약(사전/사후조건)을
  지키는지 확인한다.
- **인터페이스 분리 원칙(ISP)**: 하나의 인터페이스에 서로 무관한 오퍼레이션을
  묶지 않는다. 클라이언트가 쓰지 않는 오퍼레이션까지 강제로 의존하게 만들지 않는다.
- **의존성 역전 원칙(DIP)**: 상위 정책 컴포넌트가 하위 구현 세부사항에 직접
  의존하지 않고, 양쪽이 추상 인터페이스에 의존하도록 한다. 특히 변동성이 높은
  의존성(하드웨어, 외부 벤더 라이브러리 등)은 반드시 인터페이스 뒤로 격리한다.

## 4. 인터페이스 정의 규칙 — 컴포넌트 간 통신은 인터페이스로만

**모든 컴포넌트는 반드시 정의된 인터페이스를 통해서만 통신해야 합니다.** 컴포넌트의
내부 데이터/구현에 대한 직접 접근(전역 변수 공유, 내부 구조체 직접 참조 등)은
금지합니다.

각 인터페이스는 다음을 모두 포함해야 완성으로 취급합니다:

- **제공/요구 관계**: 어떤 컴포넌트가 이 인터페이스를 제공(provided)하고, 어떤
  컴포넌트가 요구(required)하는지 명시 (Provided/Required Interface 모델).
- **오퍼레이션/시그니처**: 오퍼레이션명, 파라미터, 반환값, 데이터 타입.
- **계약(Contract)**: 사전조건(precondition), 사후조건(postcondition), 불변조건이
  있다면 명시.
- **오류 처리 계약**: 오류/예외 발생 시 반환 방식(에러코드, 예외, 콜백 등)과 호출자의
  대응 책임을 명시.
- **동기/비동기 및 타이밍**: 호출이 동기/비동기인지, 응답 시간·주기 제약이 있다면
  명시.
- **버전**: 인터페이스 변경 시 영향받는 컴포넌트를 추적할 수 있도록 버전을 관리한다.

다이어그램은 SysML/UML Block Definition Diagram(BDD) 또는 Component Diagram으로
컴포넌트와 제공/요구 인터페이스를 표현하고, 주요 시나리오는 Sequence Diagram으로
인터페이스 호출 순서를 표현합니다. 위 "표·다이어그램 작성 형식" 규칙에 따라
원본 소스는 별도 파일로 저장하고 렌더링된 이미지만 문서에 포함합니다.

## 5. 변경 유연성 확보 전략

- **정보 은닉(Information Hiding)**: 변경 가능성이 높은 설계 결정(알고리즘,
  데이터 구조, 하드웨어 의존 세부사항)을 컴포넌트 내부에 캡슐화하고, 인터페이스에는
  노출하지 않는다.
- **변동점(Variation Point) 명시**: 향후 변형(파생 차종, 옵션 사양, 신규 센서 등)이
  예상되는 지점을 아키텍처에서 명시적으로 식별하고, 해당 지점은 인터페이스/전략
  패턴 등으로 확장 가능하게 설계한다. 예상되지 않는 모든 변경까지 과도하게 대비한
  추상화(불필요한 일반화)는 지양한다.
- **의존 방향 통제**: 안정적인 정책/도메인 컴포넌트가 변동성이 큰 세부 구현
  컴포넌트에 의존하지 않도록 의존 방향을 항상 안정된 쪽으로 향하게 한다(DIP와 연계).
- **영향 범위 분석**: 각 아키텍처 요소에 대해 "이 요소가 변경되면 어떤 인터페이스와
  어떤 요소가 영향을 받는가"를 명시하여, 변경 시 영향 분석(SUP.10 변경요청관리)이
  가능하게 한다.

## 6. 아키텍처 후보 제시 및 선정 절차

**단일 아키텍처를 바로 확정하지 않습니다.** 최소 2개 이상의 서로 다른 아키텍처
구조 후보(예: 계층형(Layered), 컴포넌트 기반(Component-Based), 파이프-필터
(Pipe-Filter), 이벤트 기반/발행-구독(Event-Driven/Pub-Sub), 마이크로커널/플러그인
등 대상 도메인에 적합한 스타일)를 제시하고, 아래 기준으로 비교표를 작성한 뒤
사용자가 선택하도록 합니다:

| 평가 기준 | 설명 |
|---|---|
| 응집도/결합도 | 1절 기준 부합 정도 |
| 변경 유연성 | 예상 변경 시나리오에 대한 영향 범위 |
| 시험 용이성(Testability) | 컴포넌트 단위/통합 시험 가능성 |
| 안전성(ASIL 분리 용이성) | 서로 다른 ASIL 요소의 분리 용이성 |
| 성능/자원 사용 | 통신 오버헤드, 메모리/CPU 사용 특성 |
| 이해 용이성 | 팀이 이해·유지보수하기 쉬운 정도 |

각 후보의 장단점과 대표 트레이드오프를 표로 정리하여 제시하고, **사용자가 명시적으로
하나를 선택하기 전까지는 상세 설계(컴포넌트/인터페이스 상세, 통합 순서) 단계로
진행하지 않습니다.**

## 7. 컴포넌트 통합 순서 정의

선정된 아키텍처의 인터페이스(제공/요구 관계)로부터 컴포넌트 간 의존 그래프를
도출하고, 이를 근거로 통합 순서를 정의합니다:

- **의존 그래프 작성**: 어떤 컴포넌트가 어떤 컴포넌트를 요구(required interface)
  하는지로 의존 방향을 표시한다(순환 의존이 발견되면 결합도 위반으로 보고하고
  아키텍처를 재검토한다).
- **통합 전략 선택**: 의존성이 적은 하위/공통 컴포넌트부터 통합하는 상향식
  (bottom-up), 핵심 시나리오 조기 검증이 필요하면 스텁을 활용한 하향식(top-down),
  또는 위험도 기반 혼합 전략 중 프로젝트 상황에 맞는 전략을 선택하고 사유를 남긴다.
- **단계별 순서표**: 통합 단계, 이번 단계에서 통합되는 컴포넌트, 필요한 스텁/드라이버,
  이 단계에서 검증 가능한 인터페이스/시나리오를 표로 제시한다.
- **SWE.4/SWE.5 연계**: 이 통합 순서는 소프트웨어 통합시험 전략(SWE.4/SWE.5)의
  입력이 되므로, 각 단계에서 검증 가능한 인터페이스를 명확히 하여 시험 케이스
  설계자가 활용할 수 있게 한다.

## 8. 추적성(Traceability)

- **ID 체계**: `NGV-ARC-<레벨>-<유형>-<일련번호>`
  - 레벨: `SYS`(시스템), `SW`(소프트웨어), `HW`(하드웨어)
  - 유형: `CMP`(컴포넌트), `IF`(인터페이스)
  - 예: `NGV-ARC-SW-CMP-0001`, `NGV-ARC-SW-IF-0002`
- **양방향 추적**: 요구사항([[requirements-analysis]] 스킬의 `NGV-<레벨>-<유형>-
  <일련번호>` ID 체계) ↔ 아키텍처 요소(컴포넌트/인터페이스) 간 양방향 링크를
  확보한다. 한쪽만 채워진 링크는 미완성으로 표시한다.
- **추적 매트릭스 갱신**: `docs/traceability/traceability-matrix.md`(또는 프로젝트가
  이미 사용 중인 위치)의 `설계요소 ID` 컬럼에 이번에 정의한 컴포넌트/인터페이스
  ID를 채워 넣는다. 컬럼이 없다면 요구사항 스킬이 정의한 컬럼 구조를 그대로 따른다.
- **일관성**: 요구사항이 변경되면 영향받는 아키텍처 요소를 찾아 보고하고(SUP.10
  변경요청관리 연계), 임의로 한쪽만 갱신하고 방치하지 않는다.

## 9. 산출 형식

아키텍처 산출물을 만들 때는 다음을 모두 포함하세요:

1. 아키텍처 후보 비교표와 선정 결과(사용자가 선택한 근거 포함)
2. 컴포넌트 목록(ID/책임/응집도 유형/SOLID 점검 결과)
3. 인터페이스 명세(제공/요구 관계, 시그니처, 계약, 오류 처리, 버전)와 BDD/Component
   Diagram(렌더링된 이미지 + 원본 소스 파일 경로)
4. 주요 시나리오의 동적 동작(Sequence/State Diagram, 렌더링된 이미지 + 원본
   소스 파일 경로)
5. 응집도/결합도 점검표(위반 사항이 있다면 재설계 여부 명시)
6. 컴포넌트 통합 순서표와 선택한 통합 전략의 근거
7. 추적 매트릭스 갱신 내역
8. 발견된 미결/트레이드오프/추가 확인 필요 사항 목록(있는 경우 반드시 별도로 보고)
