# 상세설계 참조 자료 (ISO 26262 Part 6 / A-SPICE 4.1)

이 스킬은 소프트웨어 단위(유닛) 상세설계 산출물을 작성·검토할 때 지켜야 할 규칙과
체크리스트입니다. 아래 규칙을 모두 만족하지 못하는 상세설계 초안은 미완성으로
취급하고, 어떤 항목이 빠졌는지 명시적으로 표시하세요.

## 0. 산출물 템플릿

이 프로젝트의 상세설계 산출물은 사용자가 제공하는 템플릿을 따라야 합니다.
템플릿 파일은 `D:\NGV\NGV\.claude\skills\detailed-design\templates\` 아래에 위치할
예정입니다 (예: `detailed-design-template.md`). **작업을 시작하기 전에 이
디렉터리에 템플릿 파일이 있는지 먼저 확인하세요.**

- 템플릿이 있으면: 그 템플릿의 항목/구조/표 형식을 그대로 따르고, 아래 1~8절의
  규칙은 템플릿의 각 항목을 채우는 기준으로 사용합니다.
- 템플릿이 아직 없으면: 사용자에게 아직 템플릿을 받지 못했다고 알리고, 아래 1~8절
  규칙만으로 구성한 임시 초안 구조(단위 목록, 단위 인터페이스 명세, 알고리즘/
  데이터 구조, 응집도/결합도·SOLID 점검표, 순환복잡도 점검표, 단위 검증기준,
  추적 매트릭스)를 사용해 초안을 작성하되, 템플릿 수신 후 재구성이 필요하다는
  점을 명시하세요.

## 표·다이어그램 작성 형식 (공통 규칙)

- **표 우선**: 템플릿에 특정 항목의 서식이 정의되어 있지 않은 경우, 줄글
  (prose)로 풀어쓰지 말고 적절한 표를 구성해 그 안에 작성합니다. 사용자가
  한눈에 비교·스캔할 수 있는 형태를 우선합니다. 템플릿에 이미 표/서식이
  정의되어 있다면 그 형식을 그대로 따릅니다(0절 템플릿 확인 절차와 연계).
- **다이어그램은 렌더링된 이미지로 문서에 포함**: Flowchart/Activity/State
  Machine Diagram 등 Mermaid/PlantUML 다이어그램 소스 코드를 문서 본문에
  코드 블록으로 직접 삽입하지 않습니다.
  1. 다이어그램 원본 소스는 별도 파일로 저장합니다(예:
     `diagrams/<단위ID>.mmd` 또는 `.puml`).
  2. 그 소스를 이미지(PNG 또는 SVG)로 렌더링합니다(예: Mermaid CLI `mmdc`,
     PlantUML jar 등 프로젝트에서 사용 가능한 도구).
  3. 문서에는 렌더링된 이미지만 `![설명](이미지 경로)` 형태로 삽입하고,
     원본 소스 파일 경로를 캡션/각주로 함께 명시해 추적 가능하게 합니다.
  4. 원본 소스가 변경되면 이미지도 함께 재렌더링합니다 — 이미지와 소스가
     불일치한 채로 남겨두지 않습니다.
  5. 렌더링 도구를 실행할 수 없는 환경이라면, 그 사실을 산출물에 명시하고
     원본 소스 파일 경로만 남기되(코드 블록으로 본문에 삽입하지 않음),
     "렌더링 필요"로 표시합니다. 의사코드(pseudocode)는 다이어그램이 아니므로
     이 규칙의 적용 대상이 아니며, 그대로 코드 블록으로 문서에 포함합니다.

## 1. 설계 단계 내 범위 — 구현(코드 작성)과의 경계

이 프로젝트는 CLAUDE.md에 따라 **분석 → 설계 → 구현 → 테스트** 순서를 반드시
지킵니다. 상세설계는 **설계** 단계에 속하며, **구현** 단계와 아래와 같이 명확히
구분합니다:

- 상세설계 산출물은 실제 프로그래밍 언어의 소스 코드가 아니라, 구현자가 그대로
  옮길 수 있을 만큼 충분히 구체적인 **의사코드(pseudocode)/흐름도/상태
  다이어그램 + 단위 인터페이스 명세**입니다.
- 실제 소스 코드 파일(.c/.cpp/.h 등)을 작성·생성하지 마세요. 특정 언어의 문법에
  종속된 구현(구체적 라이브러리 API 호출, 실제 컴파일 가능한 코드)은 구현 단계의
  산출물입니다.
- 이 스킬을 사용하는 에이전트는 **확정된 아키텍처**(컴포넌트/인터페이스가
  이미 선정·정의된 상태, [[architecture-design]] 스킬 산출물)를 입력으로
  전제합니다. 아키텍처가 아직 후보 단계이거나 확정되지 않았다면 임의로 새
  아키텍처를 만들지 말고, 먼저 아키텍처를 확정해야 한다고 사용자에게 알리세요.

## 2. ISO 26262 Part 6 준수 (단위 설계 원칙)

ISO 26262-6 Clause 8(소프트웨어 단위 설계 및 구현)의 설계 원칙을 적용합니다
(구현 단계에서 지켜야 할 코딩 규칙이 아니라, **설계 시점에 이미 반영해야 할
원칙**으로 적용):

- **단일 진입/단일 종료(One Entry/One Exit)**: 각 단위(함수/서브프로그램)는 진입점과
  종료점이 하나가 되도록 설계한다. 여러 개의 반환 경로가 필요하면 설계 단계에서
  흐름을 재정리한다.
- **제한된 복잡도**: 단위의 순환복잡도(Cyclomatic Complexity)를 제한한다 — 일반
  권장 상한 10, ASIL C/D는 더 낮은 상한(예: 6~8)을 권장한다. 상한을 넘으면 설계
  단계에서 단위를 분해한다.
- **제한된 크기**: 단위 하나가 과도하게 많은 처리 단계를 갖지 않도록 크기를
  제한한다.
- **구조화된 제어 흐름**: 무조건 분기(goto 상당)나 비구조적 제어 흐름을 설계에
  포함하지 않는다. 순환/재귀 사용은 제한적으로만 허용하고, 재귀를 사용할 때는
  종료조건과 최대 깊이를 명시한다.
- **숨은 데이터/제어 흐름 금지**: 단위 인터페이스에 드러나지 않는 방식으로 다른
  단위의 상태를 읽거나 변경하는 설계(숨은 전역상태 접근)를 금지한다.
- **전역 변수 제한**: 전역 상태 사용은 원칙적으로 지양하며, 불가피하면 어떤
  단위가 언제 읽고/쓰는지 설계 문서에 명시한다.
- **데이터 사용 원칙**: 사용하는 모든 데이터(변수/파라미터)는 사용 전 초기화됨을
  설계에서 보장하고, 암묵적 타입 변환에 의존하지 않는 데이터 흐름을 설계한다.
- **표기법**: 자연어 설명만으로 단위 설계를 끝내지 않는다. 半정형 표기법
  (의사코드, Flowchart/Activity Diagram, State Machine Diagram, 시퀀스 다이어그램)
  중 단위 성격에 맞는 것을 최소 1개 이상 사용한다. ASIL이 높을수록(C/D) 半정형/정형
  표기법 사용을 더 강하게 요구한다.

## 3. A-SPICE 4.1 준수 (SWE.3 정합성 — 설계 범위)

SWE.3(소프트웨어 상세설계 및 단위 구현)의 기본관행 중 **설계에 해당하는 부분**을
따릅니다(단위 구현/코딩 자체는 이 스킬의 범위가 아님, 1절 참고):

- 아키텍처 요소(컴포넌트)를 정련하여 구현 가능한 수준의 **단위**로 상세설계한다 —
  아키텍처가 정의한 컴포넌트 경계와 책임을 벗어나지 않는다.
- 각 단위의 **인터페이스**를 정의한다(4절 참고) — 아키텍처 인터페이스와 일관되어야
  한다.
- 각 단위의 **동적 동작**을 기술한다(알고리즘 흐름, 상태 전이).
- 각 단위에 대한 **검증 기준**(수용기준, 등가분할/경계값 등 시험 설계 근거)을
  정의한다 — 이 검증기준은 이후 구현(coding) 단계에서 [[tdd]] 스킬의
  Red-Green-Refactor에 따라 `unittest` 테스트로 옮겨지며, 여기서는 "무엇을
  근거로 검증할 것인가"까지만 정의하고 실제 테스트 코드 작성/실행은 하지
  않는다.
- 정의된 평가 기준(시험용이성, 이해용이성, 복잡도, 견고성)에 따라 상세설계를
  평가한 기록을 남긴다.
- 요구사항/아키텍처 요소 ↔ 단위 설계 간 **양방향 추적성**을 확보한다(8절 참고).
- 아키텍처 및 요구사항과의 **일관성**을 확보한다 — 특히 아키텍처가 정의한
  컴포넌트 간 결합도 수준을 상세설계 단계에서 훼손하지 않는다.
- CL2 수준의 산출물 관리 기준([[aspice-auditor]] 스킬 참고)에 맞게, 식별·버전·
  리뷰 증적·추적성을 갖춘 상태로 산출물을 만든다.

## 4. 단위 인터페이스 정련 규칙

아키텍처 단계에서 정의된 컴포넌트 인터페이스([[architecture-design]] 스킬 4절)를
단위(함수/모듈) 수준으로 정련합니다. 정련된 인터페이스는 다음을 모두 포함해야
완성으로 취급합니다:

- **함수 시그니처**: 함수명, 파라미터명/타입/단위(unit of measure), 반환 타입.
- **데이터 타입 상세**: 크기, 범위(min/max), 정밀도, 부호 여부 등 구현자가 추가
  해석 없이 바로 사용할 수 있는 수준.
- **계약(Contract)**: 사전조건, 사후조건, 불변조건.
- **오류 코드/예외 목록**: 발생 가능한 모든 오류 조건과 각각의 반환값/처리 방식을
  열거식으로 명시(모호하게 "오류 시 처리" 수준으로 남기지 않는다).
- **아키텍처 일관성**: 이 단위 인터페이스가 속한 컴포넌트의 제공/요구 인터페이스
  범위를 벗어나지 않는지 확인한다 — 벗어난다면 아키텍처 변경이 필요하다는 것을
  의미하므로, 임의로 상세설계에서 새 컴포넌트 간 의존을 만들지 말고 사용자에게
  보고한다.

**단위는 반드시 정의된 인터페이스를 통해서만 다른 단위/컴포넌트와 상호작용해야
합니다.** 다른 단위의 내부 변수/자료구조에 직접 접근하는 설계는 금지합니다.

## 5. 알고리즘/데이터 구조 설계

- **알고리즘**: 각 단위의 처리 로직을 의사코드 또는 Flowchart/Activity
  Diagram으로 표현한다. 의사코드는 코드 블록으로 문서에 직접 포함하고,
  Flowchart/Activity/State Machine Diagram은 위 "표·다이어그램 작성 형식"
  규칙에 따라 원본 소스를 별도 파일로 저장하고 렌더링된 이미지만 문서에
  포함한다. 상태를 갖는 단위는 State Machine Diagram으로 상태와 전이 조건을
  명시한다.
- **데이터 구조**: 단위가 사용/소유하는 데이터 구조의 필드, 타입, 불변조건
  (invariant)을 정의한다. 컴포넌트 간 공유가 필요한 데이터 구조는 반드시 4절의
  인터페이스 계약에 포함시키고, 공유 상태로 방치하지 않는다.
- **복잡도 점검**: 설계한 알고리즘의 분기/반복 구조로부터 예상 순환복잡도를
  가늠하고, 2절의 상한을 넘을 것으로 예상되면 알고리즘을 더 작은 단위로 분해한다.

## 6. 응집도/결합도 — 단위 수준 유지

상세설계는 아키텍처 단계에서 확정된 응집도/결합도 수준을 훼손하지 않아야
합니다([[architecture-design]] 스킬 1절 기준을 단위 수준에도 동일하게 적용):

- 하나의 단위는 하나의 명확한 처리를 책임진다(SRP와 연계, 7절 참고). 여러 무관한
  처리를 한 함수에 몰아넣지 않는다.
- 단위 설계 과정에서 아키텍처가 정의하지 않은 새로운 컴포넌트 간 의존이나 전역
  상태 공유가 생기지 않았는지 재확인한다. 발견되면 반드시 재설계하거나, 재설계가
  불가능하면 아키텍처 변경 필요 사항으로 보고한다(임의로 아키텍처를 우회하지
  않는다).

## 7. SOLID 원칙 적용 (단위 수준)

- **단일 책임 원칙(SRP)**: 함수/모듈 하나가 변경되어야 할 이유가 하나인지 확인한다.
- **개방-폐쇄 원칙(OCP)**: 알고리즘 변형(파라미터화 가능한 로직, 조건별 분기가
  많은 로직)은 조건 분기 나열 대신 전략 테이블/함수 포인터 등으로 확장 가능하게
  설계할 수 있는지 검토한다(과도한 일반화는 지양).
- **리스코프 치환 원칙(LSP)**: 동일 인터페이스의 여러 단위 구현체가 호출자 관점의
  계약(사전/사후조건)을 동일하게 지키는지 확인한다.
- **인터페이스 분리 원칙(ISP)**: 단위 인터페이스가 호출자마다 실제로 필요한
  오퍼레이션만 노출하는지 확인한다.
- **의존성 역전 원칙(DIP)**: 단위가 변동성 높은 하위 구현(특정 하드웨어 레지스터,
  특정 드라이버)에 직접 의존하지 않고, 아키텍처가 정의한 추상 인터페이스를 통해
  접근하는지 확인한다.

## 8. 단위 검증기준 수립 (구현 단계 TDD 입력 — 실행은 하지 않음)

각 단위에 대해 다음을 정의합니다(실제 단위시험 케이스 작성/실행은 구현
(coding) 단계에서 [[tdd]] 스킬을 사용해 수행하며, 여기서는 그 근거만
마련합니다):

- **수용기준**: 정상/경계/오류 조건별 기대 동작을 명시한다.
- **등가분할/경계값 후보**: 입력 도메인을 등가클래스로 나누고 경계값 후보를
  식별한다(전수 테스트를 요구하지 않는다).
- **커버리지 목표 근거**: ASIL에 따라 요구되는 구조 커버리지 수준(문장/분기/MC-DC
  등)이 있다면, 이 단위 구조가 그 커버리지 달성에 어떤 제약을 주는지 명시한다
  (예: 분기가 많아 MC-DC 확보를 위해 조건을 단순화 필요).

## 9. 추적성(Traceability)

- **ID 체계**: `NGV-DD-<레벨>-UNIT-<일련번호>`
  - 레벨: `SW`(소프트웨어), `HW`(하드웨어)
  - 예: `NGV-DD-SW-UNIT-0001`
- **양방향 추적**: 아키텍처 요소([[architecture-design]] 스킬의
  `NGV-ARC-<레벨>-CMP/IF-<일련번호>` ID)와 요구사항([[requirements-analysis]]
  스킬의 `NGV-<레벨>-<유형>-<일련번호>` ID) ↔ 단위 설계 간 양방향 링크를 확보한다.
  한쪽만 채워진 링크는 미완성으로 표시한다.
- **추적 매트릭스 갱신**: `docs/traceability/traceability-matrix.md`(또는 프로젝트가
  이미 사용 중인 위치)에 단위 설계 ID를 반영한다. 컬럼 구조가 없다면 요구사항
  스킬이 정의한 컬럼 구조를 확장해서 사용한다.
- **일관성**: 아키텍처가 변경되면 영향받는 단위 설계를 찾아 보고하고(SUP.10
  변경요청관리 연계), 임의로 한쪽만 갱신하고 방치하지 않는다.

## 10. 산출 형식

상세설계 산출물을 만들 때는 다음을 모두 포함하세요:

1. 단위 목록(ID/소속 컴포넌트/책임/SOLID 점검 결과)
2. 단위 인터페이스 명세(시그니처, 데이터 타입 상세, 계약, 오류 코드)
3. 알고리즘(의사코드는 코드 블록, Flowchart/State Machine은 렌더링된 이미지 +
   원본 소스 파일 경로)과 데이터 구조 정의
4. 순환복잡도/응집도·결합도 점검표(위반 사항이 있다면 재설계 여부 명시)
5. 단위별 검증기준(수용기준, 등가분할/경계값 후보, 커버리지 제약)
6. 추적 매트릭스 갱신 내역
7. 아키텍처 변경이 필요하다고 판단된 사항(있는 경우 반드시 별도로 보고)
8. 발견된 미결/트레이드오프 사항 목록(있는 경우 반드시 별도로 보고)
