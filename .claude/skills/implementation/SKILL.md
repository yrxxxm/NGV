# 구현 참조 자료 (ISO 26262 Part 6 / A-SPICE 4.1)

이 스킬은 소프트웨어 구현(코드 작성) 산출물을 만들 때 지켜야 할 규칙과
체크리스트입니다. CLAUDE.md의 프로젝트 개발 정책(분석 → 설계 → 구현 → 테스트
순서 준수, 단계별 지정 템플릿 산출물 필수, Python 3.14 + `unittest` 기반
TDD, 정량적 품질지표 준수)을 구현 단계에 적용한 것입니다. 아래 규칙을 모두
만족하지 못한 구현 산출물은 미완성으로 취급하고, 어떤 항목이 빠졌는지
명시적으로 표시하세요.

## 0. 산출물 템플릿

이 프로젝트의 구현 단계 산출물(구현 기록/추적 문서)은 사용자가 제공하는
템플릿을 따라야 합니다. 템플릿 파일은
`D:\NGV\NGV\.claude\skills\implementation\templates\` 아래에 위치할 예정입니다
(예: `implementation-record-template.md`). **작업을 시작하기 전에 이 디렉터리에
템플릿 파일이 있는지 먼저 확인하세요.**

- 템플릿이 있으면: 그 템플릿의 항목/구조/표 형식을 그대로 따르고, 아래 1~9절의
  규칙은 템플릿의 각 항목을 채우는 기준으로 사용합니다.
- 템플릿이 아직 없으면: 사용자에게 아직 템플릿을 받지 못했다고 알리고, 아래 1~9절
  규칙만으로 구성한 임시 초안 구조(구현 단위 목록, TDD RED/GREEN 로그, 코딩
  표준/품질지표 준수 점검표, 이탈 기록, 정적분석 결과, 추적 매트릭스)를 사용해
  초안을 작성하되, 템플릿 수신 후 재구성이 필요하다는 점을 명시하세요.

## 1. 구현 단계 범위와 경계 — TDD 기반 구현

CLAUDE.md에 따라 이 프로젝트의 구현(coding) 단계는 **Python 3.14 +
`unittest` 기반 TDD 방식**으로 진행합니다. 구현은 상세설계를 코드로 옮기는
작업이자 동시에 [[tdd]] 스킬의 Red-Green-Refactor 규율을 그대로 따르는
작업입니다:

- 구현의 입력은 확정된 단위 상세설계([[detailed-design]] 스킬 산출물 — 단위
  인터페이스, 알고리즘/의사코드, 데이터 구조, 검증기준)입니다. 상세설계가
  없거나 대상 단위가 상세설계에 없다면, 임의로 설계 결정을 새로 만들며 코드를
  작성하지 말고 먼저 상세설계가 필요하다고 사용자에게 알리세요.
- **각 단위를 구현하기 전에 반드시 [[tdd]] 스킬을 함께 로드하고, RED(실패하는
  `unittest` 테스트 작성) → GREEN(최소 구현) → REFACTOR 순서를 지킵니다.**
  실패하는 테스트 없이 구현 코드를 먼저 작성하지 않습니다([[tdd]] 스킬의
  Iron Law) — 이는 원본 TDD와 동일하게 이 프로젝트의 구현 단계 자체에 그대로
  적용됩니다.
- 단위 테스트 작성/실행은 구현 단계의 정당한 범위입니다. 다만 여러 컴포넌트에
  걸친 통합/인수 수준 시험, 최종 커버리지 판정 보고는 테스트 단계([[tdd]]
  스킬을 사용하는 `tester` 에이전트)의 산출물입니다.
- 구현 도중 상세설계에 없는 알고리즘/자료구조/인터페이스 변경이 필요해졌다면,
  임의로 결정하지 말고 상세설계 단계로 피드백해야 할 사항으로 보고하세요.

## 2. ISO 26262 Part 6 준수 (코딩 지침) 및 프로젝트 품질지표

ISO 26262-6 Clause 5/8.4.4의 코딩 지침 원칙을 Python 3.14 환경에 맞게
적용하고, CLAUDE.md가 정한 아래 정량적 품질지표를 **반드시** 함께 준수합니다.
이 지표들은 위반 시 3절의 도구로 측정·확인합니다:

- **명명 규칙 (필수)**: 함수명·변수명은 **3글자 이상**, **낙타 표기법
  (camelCase)**을 사용한다 — Python 관용적인 snake_case 대신 프로젝트 규칙을
  따른다(예: `calcRetryDelay`, `unitCount`). `i`, `x` 같은 한 글자 임시
  변수도 의미 있는 이름으로 대체한다.
- **함수 크기 (필수)**: 함수의 순수 코드 라인 수는 **50라인 이하**여야 한다
  (주석/빈 줄 제외). 초과하면 더 작은 함수로 분해한다.
- **순환복잡도 (필수)**: 함수의 순환복잡도는 **10 이하**여야 한다. 초과하면
  조건/분기를 단순화하거나 함수를 분해한다.
- **중복 코드 (필수)**: 중복 코드는 **최대 7라인까지만** 허용한다. 초과하는
  중복은 공통 함수/모듈로 추출한다.
- **주석 — Doxygen 방식, 20% 이상 (필수)**: 모든 주석은 Doxygen 형식
  (`"""! @brief ... @param ... @return ... """` 스타일의 Python 독스트링,
  또는 `##`)으로 작성하고, 파일 전체에서 주석 라인 비율이 **20% 이상**이어야
  한다. 코드가 하는 일을 그대로 반복하는 주석보다, 의도/제약/왜(why)를
  설명하는 주석으로 비율을 채운다.
- **강한 타이핑**: 타입 힌트(PEP 484)로 함수 시그니처의 타입을 명시하고,
  암묵적 타입 변환에 의존하지 않는다.
- **숨은 데이터/제어 흐름 금지**: 가변 전역 상태(mutable global) 공유, 다른
  모듈의 속성을 직접 수정하는 숨은 부수효과를 만들지 않는다 — 인터페이스에
  드러나지 않는 방식으로 상태를 바꾸지 않는다.
- **재귀 사용 제한**: 재귀를 사용할 때는 종료조건과 최대 깊이를 주석에
  명시한다.
- **단일 진입/단일 종료**: 함수는 가능한 한 하나의 반환 경로를 갖도록
  설계한다. 가독성을 해치지 않는 얕은 가드절(guard clause)의 다중 `return`은
  예외로 허용하되 남용하지 않는다.

## 3. 코딩 표준/품질지표 준수 확인 — 오픈소스 도구 활용

CLAUDE.md는 순환복잡도·함수라인수 등 측정 지표를 오픈소스 도구로 확인하도록
요구합니다. 아래 도구(또는 프로젝트에 이미 구성된 동등 도구)를 Bash 툴로
실행하고 결과를 산출물에 포함하세요:

- **순환복잡도**: `radon cc <경로> -s` (등급/수치 확인, 10 초과 항목 보고)
- **함수 라인 수**: `radon raw <경로>` 등으로 함수별 순수 코드 라인 수를
  집계한다.
- **중복 코드**: `pylint <경로>`의 중복 코드 검사(`R0801`,
  `min-similarity-lines`를 7로 설정)로 확인한다.
- **스타일**: `flake8`(또는 `pylint`)로 기본 스타일을 점검하되, camelCase
  명명 규칙은 이 프로젝트의 명시적 예외이므로 관련 경고(`N802`/`invalid-name`
  등)는 규칙 예외로 기록하고 억제 설정을 명시한다.
- **주석 비율**: 오픈소스 도구가 없다면 정적분석 스크립트(주석 라인 수 /
  전체 라인 수)로 자체 계산하고 그 방법을 산출물에 명시한다.
- **테스트 커버리지**: `coverage.py`로 `python -m unittest` 실행 결과의
  문장/분기 커버리지를 측정한다([[tdd]] 스킬 7절 참고).
- 도구를 실행할 수 없는 환경이라면, 2절의 체크리스트를 항목별로 수동 대조한
  **자체 점검 결과**를 산출물에 남기고, 이것이 도구 기반 정적분석을 대체하지
  않는다는 점을 명시한다.
- **이탈(Deviation) 기록**: 품질지표를 부득이하게 초과해야 하는 경우(예: 분해가
  오히려 가독성을 해치는 알고리즘), 위반 항목, 위반 사유, 영향 분석, 대안
  완화조치를 포함한 이탈 기록을 남긴다. 근거 없이 지표 위반을 방치하거나
  조용히 넘어가지 않는다.

## 4. A-SPICE 4.1 준수 (SWE.3 단위 구현 정합성)

SWE.3(소프트웨어 상세설계 및 단위 구현)의 기본관행 중 **구현(코딩)에 해당하는
부분**을 따릅니다:

- 상세설계에서 정의한 단위 인터페이스(시그니처, 데이터 타입, 계약, 오류 코드)를
  **정확히** 구현한다 — 임의로 시그니처를 바꾸거나 축약하지 않는다. 불가피하게
  달라져야 한다면 상세설계 변경 필요 사항으로 보고한다.
- [[tdd]] 스킬의 Red-Green-Refactor에 따라 각 단위에 대한 `unittest` 테스트를
  함께 작성·실행하고, 그 테스트 산출물([[tdd]] 스킬 4~5절 기준 기법/케이스
  유형/Doxygen 문서)을 구현 산출물과 함께 리뷰 대상에 포함한다.
- 구현 산출물(소스 파일/함수/테스트)을 고유하게 식별하고, 형상관리 하에 둔다
  (SUP.8 연계).
- 구현 산출물에 대한 **리뷰 기록**(6절 참고)을 남긴다.
- 요구사항 ↔ 아키텍처 요소 ↔ 단위 설계 ↔ 구현 산출물 ↔ 테스트 케이스 간
  **양방향 추적성**을 확보한다(7절 참고).
- 상세설계 및 요구사항과의 **일관성**을 확보한다.
- CL2 수준의 산출물 관리 기준([[aspice-auditor]] 스킬 참고)에 맞게, 식별·버전·
  리뷰 증적·추적성을 갖춘 상태로 산출물을 만든다.

## 5. 설계 일치성 — 응집도/결합도/SOLID 유지

구현은 상세설계와 아키텍처 단계에서 확정된 구조를 코드 수준에서 그대로
실현해야 하며, 지름길로 구조를 훼손하지 않습니다:

- 구현 코드는 정의된 인터페이스를 통해서만 다른 단위/컴포넌트와 상호작용한다.
  다른 모듈의 내부 변수에 직접 접근하거나 전역 상태를 몰래 공유하는 구현을
  금지한다([[architecture-design]] 4절, [[detailed-design]] 4·6절 기준).
- 하나의 함수/모듈이 상세설계에서 정한 책임 범위를 벗어나 다른 책임까지
  떠맡지 않았는지 확인한다(SRP 유지).
- 변동성 높은 하위 구현(하드웨어 레지스터, 벤더 라이브러리)에 대한 직접 의존이
  상세설계가 정의한 추상 인터페이스 없이 새로 생기지 않았는지 확인한다(DIP 유지).

## 6. 코드 리뷰

- 구현 완료 후, 상세설계 대비 완전성/정확성, 2절 코딩 지침/품질지표 준수,
  인터페이스 일치 여부, [[tdd]] 스킬 기준 테스트 완결성을 기준으로 한 리뷰를
  수행하고 리뷰 기록(리뷰어, 일자, 기준, 발견 사항, 처리 결과)을 남긴다.
- 에이전트가 스스로 수행한 점검은 **자체 점검(self-review)**으로 명시하고,
  사람에 의한 **공식 동료 리뷰(peer review)**가 완료된 것처럼 과장해서 보고하지
  않는다 — 공식 리뷰가 필요하면 그 사실을 산출물에 명확히 남긴다.

## 7. 추적성(Traceability)

- 구현 산출물은 별도 ID 체계를 새로 만들지 않고, 그것이 구현하는 단위 설계 ID
  ([[detailed-design]] 스킬의 `NGV-DD-<레벨>-UNIT-<일련번호>`)와 테스트 케이스
  ID([[tdd]] 스킬의 `NGV-TC-<레벨>-<일련번호>`)를 소스 코드 주석과 구현 기록
  문서 양쪽에 명시하여 연결한다.
- **양방향 추적**: 단위 설계 ID ↔ 구현 파일/함수 경로 ↔ 테스트 파일/메서드
  경로 간 링크를 확보한다. 한쪽만 채워진 링크는 미완성으로 표시한다.
- **추적 매트릭스 갱신**: `docs/traceability/traceability-matrix.md`(또는 프로젝트가
  이미 사용 중인 위치)에 구현 산출물(파일/함수 경로) 컬럼을 추가하거나 갱신한다.
- **일관성**: 상세설계가 변경되면 영향받는 구현 산출물을 찾아 보고하고(SUP.10
  변경요청관리 연계), 반대로 구현 중 발견된 설계 결함도 상세설계 단계로 피드백해
  보고한다.

## 8. 회귀 확인

- 새 단위를 구현/리팩터링한 뒤 `python -m unittest discover`로 프로젝트 전체
  테스트 스위트를 실행해 기존 테스트에 회귀가 없는지 확인한다(이는 새 단위
  자체의 RED/GREEN 검증과는 별개로, 다른 단위에 영향을 주지 않았는지 보는
  것이다).
- 실행할 수 없는 환경이라면 그 사실을 명시하고 새로 작성한 테스트 범위 내의
  결과만 보고한다.

## 9. 산출 형식

구현 산출물을 만들 때는 다음을 모두 포함하세요:

1. 구현 단위 목록(단위 설계 ID/구현 파일·함수 경로/테스트 파일·메서드 경로/상태)
2. TDD RED/GREEN 검증 로그(`python -m unittest` 실행 결과 요약)
3. 코딩 지침/품질지표 준수 점검표(2절 기준: 명명/함수라인수/순환복잡도/중복/
   주석비율, 위반 시 수정 여부 또는 이탈 기록 링크)
4. 이탈(Deviation) 기록(있는 경우)
5. 정적분석·품질지표 측정 결과(3절 도구 실행 결과, 또는 자체 점검 결과와 그 사실 명시)
6. 회귀 확인 결과(8절)
7. 코드 리뷰 기록(자체 점검/공식 리뷰 여부 구분)
8. 추적 매트릭스 갱신 내역
9. 상세설계 변경이 필요하다고 판단된 사항(있는 경우 반드시 별도로 보고)
10. 발견된 미결/트레이드오프 사항 목록(있는 경우 반드시 별도로 보고)
