# 소프트웨어 통합시험 참조 자료 (ISO 26262 Part 6 / A-SPICE 4.1 SWE.5)

이 스킬은 **소프트웨어 통합시험**(여러 컴포넌트/단위를 아키텍처가 정한 순서로
결합하며 그 결합이 올바른지 검증하는 단계, A-SPICE SWE.5) 산출물을 만들 때
지켜야 할 규칙입니다. 단위 수준 테스트(구현 단계의 TDD, [[tdd]] +
[[implementation]] 스킬)와 인수시험(SWE.6, `tester` 에이전트)의 중간
단계이며, **이 스킬이 정의하는 통합시험만의 규칙**(테스트 베이시스, 통합
순서 준수, 함수/콜 커버리지 100%)에 특화되어 있습니다. 공통 테스트 규율
(Iron Law, Red-Green-Refactor, 좋은 테스트 원칙, 테스트 함수 Doxygen
문서화, 흔한 합리화/위험 신호)은 [[tdd]] 스킬을 그대로 따르므로, 이 스킬과
함께 반드시 로드하세요. 아래 규칙을 모두 만족하지 못하는 통합시험 산출물은
미완성으로 취급하고, 어떤 항목이 빠졌는지 명시적으로 표시하세요.

## 0. 산출물 템플릿

이 프로젝트의 통합시험 산출물(시험 전략/명세/케이스/보고서)은 사용자가
제공하는 템플릿을 따라야 합니다. 템플릿 파일은
`D:\NGV\NGV\.claude\skills\integration-test\templates\` 아래에 위치할
예정입니다 (예: `integration-test-template.md`). **작업을 시작하기 전에 이
디렉터리에 템플릿 파일이 있는지 먼저 확인하세요.**

- 템플릿이 있으면: 그 템플릿의 항목/구조/표 형식을 그대로 따르고, 아래 1~9절의
  규칙은 템플릿의 각 항목을 채우는 기준으로 사용합니다.
- 템플릿이 아직 없으면: 사용자에게 아직 템플릿을 받지 못했다고 알리고, 아래
  1~9절 규칙만으로 구성한 임시 초안 구조(통합 단계별 테스트 케이스 목록,
  함수/콜 커버리지 매트릭스, RED/GREEN 로그, 추적 매트릭스)를 사용해 초안을
  작성하되, 템플릿 수신 후 재구성이 필요하다는 점을 명시하세요.

## 1. 범위와 경계

- **입력 전제조건**: 통합 대상 컴포넌트들은 이미 구현·단위시험이 완료된
  상태([[implementation]] 스킬 산출물)여야 합니다. 단위가 아직 구현되지
  않았다면 임의로 이 단계에서 구현하지 말고 구현 단계로 피드백하세요.
- **테스트 베이시스는 상세설계가 아니라 아키텍처입니다.** 이 스킬은 단위
  내부의 알고리즘이 아니라, [[architecture-design]] 스킬이 정의한
  **컴포넌트 간 인터페이스**(4절)와 **통합 순서**(7절)를 근거로 시험을
  설계합니다 — 인터페이스 명세에 없는 임의의 내부 동작을 테스트 대상으로
  삼지 않습니다.
- **인수시험(SWE.6)과의 경계**: 완전한 시스템/제품 수준의 인수 시나리오,
  이해관계자 요구사항 기준의 최종 승인 시험은 `tester` 에이전트의 범위입니다.
  이 스킬은 컴포넌트 간 결합이 아키텍처대로 동작하는지에 집중합니다.

## 2. ISO 26262 Part 6 준수 — 통합시험 기법

ISO 26262-6 Clause 10(소프트웨어 통합 및 시험)에 따라, 통합시험 케이스는
아래 기법 중 해당하는 것을 사용해 도출합니다. 하나의 통합 단계에 여러 기법을
함께 적용할 수 있습니다:

| 기법 | 적용 상황 |
|---|---|
| 요구사항 기반 테스트(Requirements-based Test) | 통합된 컴포넌트 조합이 관련 요구사항을 만족하는지 |
| 인터페이스 테스트(Interface Test) | 컴포넌트 간 인터페이스의 파라미터/데이터 타입/범위/프로토콜이 계약대로 동작하는지 |
| 고장 주입 테스트(Fault Injection Test) | 한 컴포넌트의 오류/예외 상황이 인터페이스를 통해 다른 컴포넌트에 올바르게 전파·처리되는지 |
| 자원 사용량 테스트(Resource Usage Test) | 통합된 컴포넌트들의 메모리/CPU/통신 자원 사용이 아키텍처의 자원 목표를 넘지 않는지 |
| 백투백 비교 테스트(Back-to-back Test) | 모델 기반 설계 산출물이 있는 경우, 모델 실행 결과와 통합된 코드의 실행 결과를 비교 |

테스트 케이스를 도출할 때는 다음 기법으로 구체적인 입력/시나리오를 만듭니다
(각 케이스에 사용한 기법을 [[tdd]] 스킬 4~5절 기준대로 명시):

- 동등분할(Equivalence Partitioning), 경계값 분석(Boundary Value Analysis),
  오류 추정(Error Guessing) — 인터페이스 파라미터 도메인에 적용.
- 상태 전이(State Transition) — 통합된 컴포넌트 조합이 상태를 가질 때.

## 3. 테스트 베이시스 — 아키텍처 인터페이스와 통합 순서

- **인터페이스 계약 기반 도출**: 모든 통합시험 케이스는
  [[architecture-design]] 스킬 4절에서 정의된 제공/요구 인터페이스의
  오퍼레이션, 파라미터, 사전/사후조건, 오류 코드, 동기/비동기·타이밍 계약을
  근거로 도출합니다. 인터페이스 명세에 없는 항목을 검증 대상으로 삼지
  마세요 — 명세가 불완전하면 아키텍처 단계로 피드백합니다.
- **통합 순서 준수**: [[architecture-design]] 스킬 7절의 통합 순서표를 그대로
  따릅니다. 순서를 건너뛰거나 임의로 재배열하지 않습니다. 각 통합 단계마다:
  1. 이번 단계에서 추가되는 컴포넌트와 필요한 스텁/드라이버를 확인한다.
  2. 이번 단계에서 새로 검증 가능해지는 인터페이스 목록을 확인한다.
  3. 그 인터페이스들에 대한 테스트 케이스를 모두 작성·통과시킨 뒤에만 다음
     단계로 진행한다.
- 통합 순서표가 불명확하거나 대상 컴포넌트가 순서표에 없다면, 임의로 순서를
  정하지 말고 아키텍처 단계([[architecture-design]] 스킬/`architecture-designer`
  에이전트)로 피드백해야 할 사항으로 보고하세요.

## 4. 완료 기준 — 테스트 성공률 100% / 함수 커버리지 100% / 콜 커버리지 100% (필수)

이 프로젝트는 ASIL 등급과 무관하게 통합시험 완료 조건으로 **테스트 성공률
100%, 함수 커버리지 100%, 콜 커버리지 100%**를 요구합니다(CLAUDE.md
통합 테스트 지침, ISO 26262-6의 구조 커버리지 지표를 프로젝트 표준으로
강제 적용):

- **테스트 성공률 100%**: 이번 통합 단계의 테스트를 포함해 `python -m
  unittest discover` 실행 결과에 실패(FAIL)·에러(ERROR)가 0건이어야 다음
  단계로 진행합니다.

- **함수 커버리지(Function Coverage)**: 통합 대상 소프트웨어에 존재하는
  모든 함수가 통합시험 중 최소 1회 이상 호출되어야 한다.
- **콜 커버리지(Call Coverage)**: 코드에 존재하는 모든 정적 호출 지점
  (어떤 함수가 어떤 함수를 호출하는 관계, caller→callee 엣지) 각각이 통합시험
  중 최소 1회 이상 실제로 실행되어야 한다. 함수 커버리지가 100%여도, 특정
  호출 지점(예: 조건부로만 실행되는 호출)이 실행되지 않았다면 콜 커버리지는
  100%가 아니다.

**측정 방법**:

1. **정적 기준선 확보**: `radon cc`/`ast` 기반 스크립트 또는 `code2flow`,
   `pyan3` 같은 정적 호출 그래프 도구로 통합 대상 코드의 **전체 함수
   목록**과 **전체 정적 호출 엣지 목록**을 먼저 뽑아 체크리스트로 삼는다
   (이것이 "100%"의 분모다).
2. **동적 실행 기록**: `coverage.py`(문장/함수 단위 실행 여부 확인),
   Python 표준 라이브러리 `trace` 모듈(`trace.Trace(countfuncs=True,
   countcallers=True)`) 또는 `viztracer`/`pycallgraph2` 같은 오픈소스 도구로
   통합시험 실행 중 실제 호출된 함수와 호출 엣지를 기록한다.
3. **대조 및 매트릭스 작성**: 1의 체크리스트와 2의 실행 기록을 대조하여
   **함수 커버리지 매트릭스**(함수 ID | 호출 여부 | 커버한 테스트 케이스 ID)와
   **콜 커버리지 매트릭스**(caller→callee | 호출 여부 | 커버한 테스트 케이스
   ID)를 작성한다.
4. 오픈소스 도구가 자동으로 100%를 보고하지 못하는 환경(콜 커버리지는
   범용 도구 지원이 제한적)이라면, 3의 매트릭스를 수기로 완성하고 그 산출
   방법을 산출물에 명시한다 — 도구 미사용을 숨기지 않는다.
5. **미달성 항목 처리**: 100%에 도달하지 못한 함수/호출 엣지가 있다면
   임의로 "충분하다"고 넘기지 말고, 다음 중 하나로 반드시 처리한다:
   - 해당 함수/호출을 실행하는 테스트 케이스를 추가한다(우선).
   - 정말 실행 불가능한 방어 코드 등 정당한 사유가 있다면, 사유·분석·대안
     완화조치를 포함한 이탈(deviation) 기록을 남긴다(임의 생략 금지).

## 5. 좋은 테스트 원칙 및 문서화 규칙 (공통, [[tdd]] 스킬 참고)

Iron Law, Red-Green-Refactor, 좋은 테스트 작성 원칙(뮤테이션 점검, 목(mock)
오남용 방지), 흔한 합리화/위험 신호는 [[tdd]] 스킬 2~6절을 그대로
따릅니다. 통합시험에서는 아래와 같이 확장 적용합니다:

- **Doxygen 문서화 확장**: [[tdd]] 스킬 5절의 태그(`@brief`/`@technique`/
  `@case_type`/`@unit`/`@requirement`)에 더해, 통합시험은 **`@call_edge`**
  태그를 추가로 명시합니다 — 이 테스트가 실행을 보장하는 호출 엣지를
  `<caller 컴포넌트/오퍼레이션 ID> -> <callee 컴포넌트/오퍼레이션 ID>` 형식으로
  적습니다(4절의 콜 커버리지 매트릭스와 직접 연결됩니다). `@unit` 태그에는
  이 통합시험이 걸치는 아키텍처 컴포넌트 ID
  ([[architecture-design]] 스킬 `NGV-ARC-<레벨>-CMP-<일련번호>`)를 모두
  나열합니다.
- **명명 규칙**: [[implementation]] 스킬의 프로젝트 명명 규칙(3글자 이상,
  camelCase)을 테스트 코드에도 동일하게 적용합니다.
- **결함 발견 시**: 통합시험이 결함을 드러내면, 그 결함을 재현하는 실패
  테스트를 보존한 상태에서만 관련 구현을 수정합니다(Iron Law). 수정이 특정
  단위 내부에 그친다면 해당 단위의 단위시험도 함께 보강되었는지 확인하고,
  그렇지 않다면 구현 단계로 피드백합니다.

## 6. A-SPICE 4.1 준수 (SWE.5 정합성)

- 통합 전략/순서는 아키텍처 산출물을 그대로 인용하며 독자적으로 새로 만들지
  않는다(3절).
- 통합시험 케이스는 인터페이스 계약, 요구사항, 아키텍처 요소와 양방향
  추적성을 가진다(7절).
- 통합 중 발견된 결함을 기록하고(SUP.9 연계), 수정 후 회귀 영향을 받는
  테스트를 재실행한 증적을 남긴다.
- 정의된 평가 기준(커버리지 달성률, 인터페이스 계약 준수)에 따라 통합시험
  결과를 평가한 기록을 남긴다.
- CL2 수준의 산출물 관리 기준([[aspice-auditor]] 스킬 참고)에 맞게, 식별·
  버전·리뷰 증적·추적성을 갖춘 상태로 산출물을 만든다.

## 7. 추적성(Traceability)

- **ID 체계**: 통합시험 케이스는 [[tdd]] 스킬의 `NGV-TC-<레벨>-<일련번호>`
  ID 체계를 그대로 사용하되, Doxygen 문서에 `@call_edge`와 다중 `@unit`을
  명시해 통합시험임을 구분한다.
- **양방향 추적**: 요구사항 ID ↔ 아키텍처 인터페이스 ID(`NGV-ARC-...-IF-...`)
  ↔ 통합시험 케이스 ID ↔ 시험 결과 간 양방향 링크를 확보한다. 한쪽만 채워진
  링크는 미완성으로 표시한다.
- **추적 매트릭스 갱신**: `docs/traceability/traceability-matrix.md`의
  `시험케이스 ID`/`시험결과` 컬럼을 갱신하고, 함수/콜 커버리지 매트릭스를
  별도 산출물로 추가(또는 갱신)한다.

## 8. 산출 형식

통합시험 산출물을 만들 때는 다음을 모두 포함하세요:

1. 통합 순서에 따른 단계별 테스트 케이스 목록(ID/기법/케이스 유형/
   `@call_edge`/Doxygen 설명)
2. RED/GREEN 검증 로그
3. 함수 커버리지 매트릭스(함수별 실행 여부, 100% 미달 시 계획/이탈 기록)
4. 콜 커버리지 매트릭스(호출 엣지별 실행 여부, 100% 미달 시 계획/이탈 기록)
5. 발견된 결함과 재현 테스트, 수정 및 재검증 기록(있는 경우)
6. 추적 매트릭스 갱신 내역
7. 아키텍처(인터페이스/통합 순서) 변경이 필요하다고 판단된 사항(있는 경우)
8. 발견된 미결/트레이드오프 사항 목록(있는 경우 반드시 별도로 보고)

## 9. 태도 원칙 (참고 — 에이전트 지침과 함께 적용)

- 아키텍처가 정의한 통합 순서를 임의로 건너뛰거나 재배열하지 마세요.
- 함수/콜 커버리지 100%를 "대략 다 됐으니 충분"으로 넘기지 마세요 — 매트릭스로
  증명하거나 이탈 기록을 남기세요.
- 인터페이스 명세에 없는 내부 동작을 통합시험 대상으로 임의로 확장하지
  마세요.
