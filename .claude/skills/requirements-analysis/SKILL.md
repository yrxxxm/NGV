# 요구사항 분석 참조 자료 (ISO 26262 / A-SPICE 4.1)

이 스킬은 요구사항 산출물을 작성·분석할 때 지켜야 할 규칙과 체크리스트입니다.
아래 규칙을 모두 만족하지 못하는 요구사항 초안은 미완성으로 취급하고, 어떤 항목이
빠졌는지 명시적으로 표시하세요.

## 0. 산출물 템플릿

이 프로젝트의 요구사항 산출물은 사용자가 제공하는 템플릿을 따라야 합니다.
템플릿 파일은 `D:\NGV\NGV\.claude\skills\requirements-analysis\templates\` 아래에
위치할 예정입니다 (예: `requirement-template.md`). **작업을 시작하기 전에 이
디렉터리에 템플릿 파일이 있는지 먼저 확인하세요.**

- 템플릿이 있으면: 그 템플릿의 항목/구조/표 형식을 그대로 따르고, 아래 1~6절의
  규칙은 템플릿의 각 항목을 채우는 기준으로 사용합니다.
- 템플릿이 아직 없으면: 사용자에게 아직 템플릿을 받지 못했다고 알리고, 아래 1~6절
  규칙만으로 구성한 임시 초안 구조(요구사항 ID, 제목, 설명, 근거, 유형, ASIL,
  검증기준, 검증방법, 추적 링크, 상태)를 사용해 초안을 작성하되, 템플릿 수신 후
  재구성이 필요하다는 점을 명시하세요.

## 1. ISO 26262 준수 (요구사항 속성)

ISO 26262-8 Clause 6(요구사항 관리)의 원칙을 따릅니다:

- **고유 식별자**: 모든 요구사항은 고유 ID를 가진다 (제안 형식은 5절 참고).
- **원자성(Atomic)**: 하나의 요구사항은 하나의 요구만 담는다. "그리고/또는"으로
  여러 요구를 묶지 않는다 — 묶여 있으면 분리한다.
- **ASIL 등급**: 안전 목표(Safety Goal)에서 파생된 요구사항은 ASIL 등급(QM, A, B,
  C, D)을 명시하고, 상위 안전목표/기술안전요구사항으로부터의 분해(decomposition)
  근거를 남긴다.
- **추상화 수준 일치**: 요구사항은 해당 레벨(아이템/시스템/소프트웨어/하드웨어)에
  맞는 추상화 수준을 유지한다 — 시스템 요구사항 단계에서 구현 세부사항(특정 알고리즘,
  특정 변수명)을 규정하지 않는다.
- **검증 가능성**: "안전해야 한다", "충분히 빨라야 한다" 같은 검증 불가능한 표현을
  금지하고, 측정 가능한 기준으로 표현한다.
- **분류**: 요구사항이 기능/비기능/안전/인터페이스 중 무엇인지 명시한다.

## 2. A-SPICE 4.1 준수 (프로세스 정합성)

SYS.2(시스템 요구사항 분석), SWE.1(소프트웨어 요구사항 분석)의 기본관행에 따릅니다:

- 이해관계자 요구사항/상위 요구사항과의 정합성을 확보하고, 근거(rationale)와 출처를
  명시한다.
- 요구사항의 우선순위와 상태(초안/검토중/승인/구현중/검증완료)를 관리한다.
- 인터페이스 요구사항은 별도로 식별하고 관련 시스템/컴포넌트를 명시한다.
- 요구사항 변경 시 영향 분석과 이력을 남긴다 (SUP.10 변경요청관리와 연계).
- CL2 수준의 산출물 관리 기준([[aspice-auditor]] 스킬 참고)에 맞게, 식별·버전·
  리뷰 증적·추적성을 갖춘 상태로 산출물을 만든다.

## 3. 기능 요구사항 — UML/SysML 다이어그램화

기능 요구사항은 텍스트 설명과 함께 최소 1개 이상의 다이어그램으로 표현합니다.
다이어그램은 Mermaid 또는 PlantUML 코드 블록으로 작성하고(텍스트 기반 저장소에서
버전관리 가능하도록), 요구사항 ID를 다이어그램 캡션/주석에 명시해 추적 가능하게
합니다.

요구사항 성격에 맞는 다이어그램을 선택하세요:

| 요구사항 성격 | 권장 다이어그램 |
|---|---|
| 시스템/액터 상호작용, 기능 범위 | Use Case Diagram |
| 동작 순서, 메시지 흐름 | Sequence Diagram |
| 상태 전이, 모드 | State Machine Diagram |
| 처리 절차, 알고리즘 흐름 | Activity Diagram |
| 시스템/컴포넌트 구조, 인터페이스 | Block Definition Diagram (SysML BDD) |
| 컴포넌트 간 연결/데이터 흐름 | Internal Block Diagram (SysML IBD) |
| 요구사항 간 관계(derive/satisfy/verify) | Requirement Diagram (SysML) |

각 다이어그램에는 "이 다이어그램이 어떤 요구사항 ID를 표현하는지"를 반드시
명시하세요. 다이어그램만 있고 텍스트 요구사항이 없거나, 텍스트만 있고 다이어그램이
없는 기능 요구사항은 미완성으로 취급합니다.

## 4. 비기능 요구사항 — ISO 25010 기준

비기능 요구사항은 반드시 ISO/IEC 25010 품질특성 중 하나 이상에 매핑하고, 그
특성명을 명시합니다:

1. **기능 적합성(Functional Suitability)** — 완전성, 정확성, 적절성
2. **성능 효율성(Performance Efficiency)** — 시간 반응성, 자원 사용성, 용량
3. **호환성(Compatibility)** — 공존성, 상호운용성
4. **사용성(Usability)** — 인식적합성, 학습성, 운용성, 오류방지, UI심미성, 접근성
5. **신뢰성(Reliability)** — 성숙성, 가용성, 결함허용성, 복구성
6. **보안성(Security)** — 기밀성, 무결성, 부인방지, 책임추적성, 진본성
7. **유지보수성(Maintainability)** — 모듈성, 재사용성, 분석용이성, 수정용이성,
   시험용이성
8. **이식성(Portability)** — 적응성, 설치성, 대체성

각 비기능 요구사항은 다음을 모두 포함해야 합니다:

- **품질특성/부특성**: 위 8개 중 어디에 속하는지
- **정량적 수용기준**: 측정 가능한 지표 + 임계값 + 측정 조건 (예: "정상 부하 조건에서
  95퍼센타일 응답시간 200ms 이하" — "빨라야 한다" 같은 표현 금지)
- **검증방법**: 시험(Test)/분석(Analysis)/검사(Inspection)/시연(Demonstration) 중
  하나를 명시하고, 실행 가능한 절차(환경, 도구, 측정 방법, 합격/불합격 판정 기준)를
  구체적으로 제시

**실행 불가능한 검증방안 금지**: 다음과 같은 검증방안은 제시하지 마세요.
- 반증 불가능한 목표 (예: "절대 실패하지 않는다", "100% 안전함을 증명한다")
- 측정 불가능하거나 조건이 없는 기준 (예: "충분히 빠르다", "사용하기 편해야 한다"만
  적고 지표가 없는 경우)
- 현재 가용하지 않은 도구/환경을 전제로 하는 검증(가용성 확인 없이 특정 벤치마크
  장비나 미확보 테스트베드를 전제)
- 무한/전수 검증을 요구하는 방안 (예: "모든 입력 조합에 대해 테스트") — 대신
  동등분할/경계값 분석 등 실행 가능한 샘플링 전략으로 대체 제시

품질특성에 맞는 검증방법 선택 예시:
- 성능 효율성 → 부하시험/성능측정 (Test)
- 신뢰성 → 고장주입시험, MTBF 분석 (Test/Analysis)
- 보안성 → 취약점 스캔, 침투시험, 코드 정적분석 (Test/Analysis/Inspection)
- 사용성 → 사용성 평가 세션, 체크리스트 기반 휴리스틱 평가 (Demonstration/Inspection)
- 유지보수성 → 정적분석 지표(순환복잡도, 결합도), 코드 리뷰 체크리스트 (Analysis/Inspection)
- 이식성 → 대상 플랫폼별 설치/실행 시험 (Test)

## 5. 명확성(Clarity) 확보

모든 요구사항은 다음 규칙을 지켜 사람이 오해 없이 이해할 수 있게 작성합니다
(INCOSE 요구사항 작성 규칙 기반):

- **EARS 패턴 권장**: 예) "〈트리거/조건〉일 때, 〈시스템명〉은 〈행위〉해야 한다."
  (이벤트 기반: "~이 발생하면", 상태 기반: "~인 동안", 선택적: "~인 경우에 한해",
  무조건: 상시 요구)
- **능동태, 단정형 조동사**: "~해야 한다(shall)"를 사용하고 "~할 수도 있다" 같은
  모호한 조동사를 피한다. "할 수 있다(may/can)"는 선택 요구에만 사용한다.
- **모호어 금지**: "적절히", "충분히", "가능한 한", "일반적으로", "사용자 친화적으로"
  같이 정량화되지 않은 표현을 금지한다. 반드시 수치/조건으로 대체한다.
- **약어/용어 정의**: 처음 등장하는 약어와 전문용어는 용어집(6절 참고)에 정의하고
  이후 동일 용어를 일관되게 사용한다.
- **하나의 문장에 하나의 요구**: and/or로 여러 요구를 묶지 않는다.
- **부정 요구 지양**: "~하지 않아야 한다"보다는 시스템이 해야 할 긍정 동작으로
  표현하되, 안전 관련 금지사항은 예외적으로 명확한 부정 요구로 남긴다.

## 6. 추적성(Traceability) 확보

**추적 방안**: 각 요구사항은 고유 ID를 가지며, 추적 매트릭스 파일을 통해 상위/하위
산출물과 양방향으로 연결합니다.

- **ID 체계**: `NGV-<레벨>-<유형>-<일련번호>`
  - 레벨: `STK`(이해관계자), `SYS`(시스템), `SWE`(소프트웨어), `HWE`(하드웨어)
  - 유형: `FR`(기능), `NFR`(비기능), `SR`(안전)
  - 예: `NGV-SYS-FR-0001`, `NGV-SWE-NFR-0003`, `NGV-SYS-SR-0002`
- **추적 매트릭스**: `docs/traceability/traceability-matrix.md` (또는 프로젝트가
  이미 사용 중인 위치가 있으면 그에 맞춘다)에 다음 컬럼을 유지합니다:
  `요구사항 ID | 상위 요구사항/이해관계자요구 ID | 설계요소 ID | 시험케이스 ID |
  시험결과 | 상태`
- **양방향**: 위(상위 요구/근거)와 아래(설계, 코드, 시험 케이스, 시험 결과) 양쪽
  방향 링크를 모두 채웁니다. 한쪽만 채워진 링크는 미완성으로 표시합니다.
- **유지 방법**: 요구사항을 신규 작성하거나 변경할 때마다 이 스킬을 사용하는
  에이전트가 추적 매트릭스를 함께 갱신합니다. 상위 요구사항 변경 시 영향받는
  하위 항목을 모두 찾아 영향 분석 결과를 남깁니다 (SUP.10 변경요청관리 연계).

## 7. 일관성(Consistency) 확보

- **용어 일관성**: 프로젝트 용어집(`docs/glossary.md`, 없으면 새로 생성 제안)에
  없는 동의어를 새로 만들지 않는다. 같은 개념은 항상 같은 용어로 지칭한다.
- **단위/값 일관성**: 물리량 단위, 시간 단위, 임계값 표기 방식을 프로젝트 전체에서
  통일한다.
- **모순 검사**: 새 요구사항을 추가할 때 기존 요구사항과 상충하는 내용이 없는지
  대조하고, 상충이 발견되면 사용자에게 명시적으로 보고한다(임의로 한쪽을 선택해
  덮어쓰지 않는다).
- **양식 일관성**: 0절의 템플릿(또는 임시 구조)을 모든 요구사항에 동일하게 적용한다.

## 8. 산출 형식

요구사항 산출물을 만들 때는 다음을 모두 포함하세요:

1. 요구사항 목록(템플릿 형식, 각 항목에 ID/설명/근거/유형/ASIL(해당 시)/
   품질특성(비기능 시)/수용기준/검증방법/상태 포함)
2. 기능 요구사항에 대한 UML/SysML 다이어그램(코드 블록)과 요구사항 ID 매핑
3. 추적 매트릭스 갱신 내역
4. 용어집에 추가된 신규 용어(있는 경우)
5. 발견된 모호성/모순/미결 사항 목록 (있는 경우 반드시 별도로 보고)
