# SW 시스템 테스트 케이스 생성

## 개요

SW 요구사항 명세서 기반으로 SW 시스템 테스트 케이스를 생성하기 위한 방법론 스킬입니다. 이 스킬은 "무엇을 근거로, 어떤 기법으로, 어떤 원칙으로" 테스트 케이스를 설계할지에 대한 방법론만 정의합니다. 요구사항 분석, 사용자와의 확인, 실제 산출물(xlsx) 작성은 이 스킬을 사용하는 에이전트(예: `sw-system-tester` 서브에이전트)가 수행합니다.

## 역할 경계 (다른 스킬/에이전트와의 관계)

이 프로젝트는 A-SPICE SWE.6(소프트웨어 인수/자격시험)을 **설계(명세)**와
**자동화(실행 코드)** 두 활동으로 나누어 담당합니다. 이 스킬은 앞의 것만
다룹니다:

- **이 스킬의 산출물은 실행 가능한 자동화 코드가 아니라 명세서(xlsx)입니다.**
  설계된 케이스를 실제 `unittest` 자동화 코드로 옮기고 실행·결함 대응까지
  하는 것은 `tester` 서브에이전트와 `tdd` 스킬의 몫이며, 이 스킬은 그 경계를
  넘지 않습니다.
- **SWE.5(소프트웨어 통합시험)와는 다릅니다.** 아키텍처 설계서의 컴포넌트 간
  인터페이스/통합 순서를 근거로 한 통합시험, 그리고 함수/콜 커버리지 100%
  달성은 `integration-tester` 서브에이전트와 `integration-test` 스킬의
  몫입니다. 이 스킬은 SW 요구사항 명세서를 직접 근거로 한 블랙박스 설계에
  집중합니다.
- **기법 카탈로그의 중복 방지**: 아래 "적용 대상 테스트 기법"의 경계값/
  동치클래스/경험 기반 기법은 코드 수준 화이트박스 테스트 기법을 다루는
  `tdd` 스킬의 카탈로그와 개념적으로 겹칩니다. 이는 의도된 것입니다 — 이
  스킬은 **요구사항 명세서 기반 블랙박스 설계**에, `tdd` 스킬은 **이미 정해진
  케이스를 코드로 구현할 때의 화이트박스/코드 수준 판단**(결정테이블, 상태
  전이 등 포함)에 각각 적용됩니다. 이 스킬로 이미 기법과 긍정/부정 분류를
  정한 케이스를 `tester`가 자동화할 때는 그 값을 그대로 재사용하고 새로
  판단하지 않습니다.

## 기반지식

- **ISO 26262 Part 6**: 소프트웨어 단위/통합/시스템 테스트에 대한 요건. 특히 ASIL 등급이 할당된 요구사항은 판정기준의 전 분기(경계값, 조건 조합)를 빠짐없이 검증해야 합니다.
- **A-SPICE SWE.4, SWE.5, SWE.6**: 소프트웨어 단위 검증, 통합 시험, 시스템 시험에 대한 Base Practice. 양방향 추적성(요구사항 ↔ 테스트 케이스)과 표준화된 시험 절차를 요구합니다.
- **ISO 29119 및 ISTQB**: 테스트 시나리오·테스트 케이스 설계 프로세스와 용어 체계(긍정/부정 분류 등)의 근거로 사용합니다.
- **ISO 25000 (SQuaRE)**: 비기능(품질) 요구사항을 분류하는 기준입니다. 비기능 테스트 케이스는 이 표준의 품질 특성(예: 기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)별로 그룹화합니다.

## 적용 대상 테스트 기법

요구사항의 성격에 맞춰 아래 기법 중에서 선택하여 적용하고, 각 테스트 케이스의 "사용 기법" 항목에 실제로 적용한 기법을 명시합니다.

- **경계값 분석**: 검증기준에 수치·범위·임계값이 있는 경우, 경계값 미만/경계값/경계값 초과를 각각 별도 케이스로 도출합니다.
- **동치 클래스(동등분할)**: 입력 도메인을 유효/무효 클래스로 나누어 대표값을 도출합니다.
- **조합 테스트(전 조건 조합)**: 관련 조건 수가 적어 전수 조합이 실행 가능한 범위일 때 우선 적용합니다.
- **페어와이즈**: 조건·값의 조합 수가 많아 전수 조합 테스트가 비현실적인 경우에 대체 적용합니다.
- **엣지 케이스**: 정상 범위의 극단, 동시성/타이밍 등 일반 분석 기법으로 포착되지 않는 특이 조건을 다룹니다.
- **경험 기반 테스트**: 유사 시스템의 결함 이력이나 QA 경험에 근거해 오류를 추정합니다(오류 추정, 탐색적 테스트 등).

## 작성 원칙

- 의미 없이 테스트 커버리지 수치 달성만을 목적으로 하는 케이스는 생성하지 않습니다.
- 테스트의 예상 결과를 임의로 가정하지 않습니다. 명세서에 근거가 없다면 이 스킬을 사용하는 에이전트가 사용자에게 확인을 받아야 합니다.
- 프로젝트에서 정한 테스트 커버리지 목표(예: CLAUDE.md에 명시된 기준)를 준수합니다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성합니다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, 이 스킬을 사용하는 에이전트를 통해 사용자 검토를 받습니다.
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하고 싶은 테스트 케이스는 테스트 케이스명 끝에 "(제안)"이라고 표시해 구분합니다.
- 사용한 테스트 설계 기법을 각 케이스에 명시합니다.

## 도구 사용

- 페어와이즈 조합을 생성할 때는 오픈소스인 PICT를 사용합니다.
- 전수 조합(모든 조건의 조합)을 생성할 때는 PICT의 `/o:max` 옵션을 사용합니다.

## 산출물 템플릿

이 프로젝트의 시스템 테스트 케이스 산출물(xlsx)은 사용자가 제공하는 템플릿을
따라야 합니다. 템플릿 파일은
`D:\NGV\NGV\.claude\skills\sw-system-test\templates\` 아래에 위치할
예정입니다. **작업을 시작하기 전에 이 디렉터리에 템플릿 파일이 있는지 먼저
확인하세요.**

- 템플릿이 있으면: 그 템플릿의 시트 구조/컬럼을 그대로 따르고, 아래 "산출물
  구조"는 템플릿의 각 항목을 채우는 기준으로 사용합니다.
- 템플릿이 아직 없으면: 사용자에게 아직 템플릿을 받지 못했다고 알리고, 아래
  "산출물 구조"만으로 구성한 임시 구조로 작성하되, 템플릿 수신 후 재구성이
  필요하다는 점을 명시하세요.

## 산출물 구조

- 기능 요구사항에 대한 테스트 케이스: "테스트 케이스" 시트
- 비기능 요구사항에 대한 테스트 케이스: 별도의 "비기능 테스트 케이스" 시트, ISO 25000 품질 특성별로 구분
- 요구사항 원문에 없거나 원문보다 엄격하게 사용자 확인을 거쳐 확정한 판정기준: "확정 근거" 열에 확정 일자와 승인 주체 기록

## 추적성

- **테스트 케이스 ID**: 별도 체계를 새로 만들지 않고, `tdd` 스킬의
  `NGV-TC-<레벨>-<일련번호>` 체계를 그대로 사용합니다(예: `NGV-TC-SW-0101`).
  이렇게 해야 이후 `tester`가 자동화 코드로 옮길 때, 그리고 프로젝트 공통
  추적 매트릭스에서 동일한 케이스를 하나의 ID로 추적할 수 있습니다.
- **양방향 추적**: 요구사항 ID(`requirements-analysis` 스킬 체계) ↔ 이
  테스트 케이스 ID 간 링크를 "대상 요구사항" 컬럼에 명시합니다.
- **추적 매트릭스 갱신**: `docs/traceability/traceability-matrix.md`의
  `시험케이스 ID` 컬럼에 이 xlsx 산출물의 케이스 ID(및 파일 경로)를
  반영하도록, 이 스킬을 사용하는 에이전트에게 안내합니다.
