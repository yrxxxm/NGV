# TDD 참조 자료 (ISO 26262 Part 6 / A-SPICE 4.1)

출처: [obra/superpowers](https://github.com/obra/superpowers)의
`test-driven-development` 스킬을 이 프로젝트의 개발 정책(CLAUDE.md)과
ISO 26262 Part 6 / A-SPICE 4.1 요구사항에 맞게 각색한 참조 자료입니다. 아래
규칙을 모두 만족하지 못하는 테스트 산출물은 미완성으로 취급하고, 어떤 항목이
빠졌는지 명시적으로 표시하세요.

## 0. 산출물 템플릿

이 프로젝트의 테스트 산출물(시험 명세/케이스/보고서)은 사용자가 제공하는
템플릿을 따라야 합니다. 템플릿 파일은
`D:\NGV\NGV\.claude\skills\tdd\templates\` 아래에 위치할 예정입니다 (예:
`test-case-template.md`). **작업을 시작하기 전에 이 디렉터리에 템플릿 파일이
있는지 먼저 확인하세요.**

- 템플릿이 있으면: 그 템플릿의 항목/구조/표 형식을 그대로 따르고, 아래 1~9절의
  규칙은 템플릿의 각 항목을 채우는 기준으로 사용합니다.
- 템플릿이 아직 없으면: 사용자에게 아직 템플릿을 받지 못했다고 알리고, 아래 1~9절
  규칙만으로 구성한 임시 초안 구조(테스트 케이스 목록, 각 케이스의 기법/케이스
  유형/Doxygen 설명, RED/GREEN 로그, 추적 매트릭스)를 사용해 초안을 작성하되,
  템플릿 수신 후 재구성이 필요하다는 점을 명시하세요.

## 1. 이 스킬을 사용하는 두 국면 — 구현(coding) 단계와 테스트 단계

CLAUDE.md에 따라 이 프로젝트는 Python 3.14와 `unittest`를 사용하며, **구현
(coding) 단계 자체를 TDD 방식으로 진행**합니다. 즉 원본 TDD의 "구현 코드를
작성하기 전에 반드시 실패하는 테스트를 먼저 작성한다"는 규율을 이 프로젝트는
구현 단계에서 그대로 적용합니다. 이 스킬은 아래 두 국면에서 공통으로
사용되며, 국면에 따라 대상 범위가 다릅니다:

- **구현(coding) 단계 — 단위 수준 TDD** ([[implementation]] 스킬과 함께 사용,
  `implementer` 에이전트 담당): 상세설계([[detailed-design]] 스킬 8절)의 단위
  검증기준으로부터 `unittest` 테스트를 먼저 작성하고(RED), 그 단위를 새로
  구현하면서 최소 코드로 통과시키고(GREEN), 리팩터링합니다(REFACTOR). 이
  국면에서는 아직 존재하지 않는 기능을 새로 만드는 것이므로 원본 TDD의
  Iron Law가 문자 그대로 적용됩니다 — **실패하는 테스트 없이 구현 코드를
  작성하지 않습니다.**
- **테스트 단계 — 통합/인수 수준 검증** (`tester` 에이전트 담당): 이미
  구현·단위시험이 끝난 컴포넌트들을 [[architecture-design]] 스킬 7절의 통합
  순서에 따라 통합하며, 통합/인수 시나리오에 대한 `unittest` 테스트 스위트를
  작성합니다. 이 국면에서 결함이 발견되면, **그 결함을 재현하는 실패 테스트를
  먼저 확보한 상태에서만** 관련 구현을 수정합니다(Iron Law는 결함 수정 루프에도
  동일하게 적용). 요구사항에는 있으나 어떤 단위에도 구현되어 있지 않은 기능을
  발견했다면, 임의로 이 단계에서 새로 구현하지 말고 구현 단계로 피드백합니다.

두 국면 모두 아래 2~9절의 규율(Iron Law, Red-Green-Refactor, 좋은 테스트 원칙,
기법/케이스 분류, Doxygen 문서화, 추적성)을 동일하게 따릅니다. Python 코드
품질지표(함수 라인 수, 순환복잡도, 중복 코드, 주석 비율, 명명 규칙)는
[[implementation]] 스킬 2절에 정의되어 있으며, 테스트 코드 자체에도 동일하게
적용됩니다.

## 2. Iron Law와 Red-Green-Refactor

```
실패하는 테스트 없이는 (신규 기능이든 결함 수정이든) 프로덕션 코드를 작성하지 않는다.
```

테스트를 작성하지 않고 코드를 먼저 작성했다면, 그 코드를 되돌리고 테스트부터
다시 작성하세요. "일단 이번만"이라는 예외는 없습니다.

1. **RED — 실패하는 테스트 작성**: 하나의 동작만 검증하는 최소한의
   `unittest` 테스트 메서드를 작성합니다. 이름은 검증 대상 동작을 명확히
   드러내야 합니다(명명 규칙은 5절 참고).
2. **RED 검증 (필수, 절대 건너뛰지 않음)**: 실제로 `python -m unittest`로
   테스트를 실행해 다음을 확인합니다 — 테스트가 실패하는가(에러가 아니라
   실패인가), 실패 메시지가 기대한 것인가, 오타가 아니라 기능/결함 때문에
   실패하는가. 테스트가 처음부터 통과한다면 3절의 뮤테이션 점검으로 유효성을
   재확인하세요.
3. **GREEN — 최소한의 코드**: 테스트를 통과시키는 가장 단순한 코드를
   작성합니다. 테스트가 요구하지 않는 기능 추가, 다른 코드 리팩터링, "개선"을
   함께 하지 않습니다. [[implementation]] 스킬 2절의 품질지표(함수 50라인
   이하, 순환복잡도 10 이하 등)를 이 시점에도 지킵니다.
4. **GREEN 검증 (필수)**: 대상 테스트와 기존 테스트 전체(`python -m unittest
   discover`)가 통과하는지, 출력이 깨끗한지(에러/경고 없음) 확인합니다. 다른
   테스트가 깨지면 그 자리에서 수정합니다.
5. **REFACTOR**: 테스트가 모두 통과한 뒤에만 중복 제거, 이름 개선, 헬퍼 추출을
   수행합니다. 이 단계에서 새로운 동작을 추가하지 않습니다.

## 3. 좋은 테스트 작성 원칙

- **테스트가 잡아내는 결함을 먼저 명시한다**: 테스트 본문을 쓰기 전에 "이
  테스트를 실패시킬 프로덕션 코드 변경이 무엇인가"를 스스로 답할 수 있어야
  합니다. 답할 수 없다면 관찰 가능한 동작 중심으로 테스트를 다시 설계하세요.
- **기대값은 독립적으로 도출한다**: 검증 대상 코드나 그 헬퍼로 계산한 값을
  기대값으로 재사용하지 않습니다(미러 어서션 금지). 리터럴 값이나 손으로 검증한
  픽스처를 사용하세요.
- **변경 감지기 금지**: 의도적 설계 결정(상수 값, 내부 구조)만 바뀌어도 깨지고
  실제 버그에는 반응하지 않는 테스트를 작성하지 않습니다. 그 결정에 의존하는
  실제 동작을 검증하세요.
- **실제 동작을 검증하고 목(mock)을 검증하지 않는다**: 목 객체의 존재/호출
  여부만 확인하는 어서션은 그 컴포넌트에 대해 아무것도 증명하지 않습니다.
  `unittest.mock`을 사용해야 한다면, 느리거나 외부 의존적인 부분만 대체하고
  실제 부수효과를 먼저 파악한 뒤 그 아래 계층만 목으로 만드세요.
- **목 응답은 실제 구조를 완전히 반영한다**: 테스트가 읽는 필드만이 아니라
  실제 문서화된 전체 필드를 미러링합니다.
- **테스트 전용 코드는 테스트 유틸리티에 둔다**: 프로덕션 클래스에 테스트만
  호출하는 정리(cleanup) 메서드를 추가하지 않습니다.
- **뮤테이션 점검**: 테스트를 마치기 전, 대상 코드를 머릿속으로 변형해 봅니다
  (잘못된 상수/분기, 누락된 상태 변경/부수효과, 빈 값·기본값 반환, 경계값/널/
  권한 없음 입력에 대한 검증 누락). 각 변형에 대해 최소 하나의 테스트가
  실패해야 합니다. 아무 테스트도 잡아내지 못하면 그 동작은 보호되지 않은
  것이거나 테스트가 동어반복입니다.

## 4. 테스트 설계 기법과 케이스 분류 (필수 명시 항목)

이 절은 **코드 수준(화이트/그레이박스)**에서 `unittest` 테스트를 새로
작성할 때 기법과 케이스 유형을 스스로 정하는 기준입니다. 만약 자동화하려는
테스트가 **이미 [[sw-system-test]] 스킬(SWE.6 요구사항 기반 블랙박스 설계,
xlsx 명세)로 설계되어 기법과 긍정/부정 분류가 정해져 있다면, 이 절로 다시
판단하지 말고 그 명세에 적힌 값을 그대로 옮기세요** — 같은 케이스에 대해
두 스킬이 서로 다른 기법을 매기는 불일치를 방지하기 위함입니다.

**모든 테스트 케이스는 다음 두 가지를 반드시 명시해야 완성으로 취급합니다:**

- **사용한 테스트 설계 기법**: 아래 중 이 테스트를 도출한 기법을 명시합니다
  (하나 이상 가능).
  | 기법 | 적용 상황 |
  |---|---|
  | 동등분할(Equivalence Partitioning) | 입력 도메인을 유효/무효 클래스로 분할 |
  | 경계값 분석(Boundary Value Analysis) | 범위의 경계, 경계 ±1 |
  | 결정 테이블(Decision Table) | 여러 조건의 조합에 따른 결과 |
  | 상태 전이(State Transition) | 상태를 가진 단위의 상태/전이 검증 |
  | 오류 추정(Error Guessing) | 과거 결함 패턴, 예상되는 실수 |
  | 원인-결과 그래프(Cause-Effect Graphing) | 복잡한 조건 조합의 논리적 관계 |
- **긍정/부정 케이스 여부**: 각 테스트가 **Positive**(정상/유효 입력에 대한
  기대 동작 검증)인지 **Negative**(비정상/무효/경계 초과 입력에 대한 오류 처리·
  거부 동작 검증)인지 명시합니다. 하나의 단위에 대해 Positive 케이스만 있고
  Negative 케이스가 없다면 미완성으로 취급합니다(안전 관련 단위는 특히
  Negative 케이스를 빠짐없이 다룹니다).

기법과 케이스 유형이 명시되지 않은 테스트는 5절의 문서화 규칙 위반이며,
산출물에 그대로 포함하지 않고 보완합니다.

## 5. 테스트 함수 문서화 규칙 (Doxygen 형식, 필수) 및 명명 규칙

**모든 `unittest` 테스트 메서드는 Doxygen 형식의 목적 설명을 독스트링으로
포함해야 합니다.** Python에서는 `"""! ... """` 형식(Doxygen의 Python 필터가
인식하는 형식)을 사용하고, 아래 태그를 반드시 포함합니다:

```python
import unittest

class TestRetryOperation(unittest.TestCase):
    def testRetrySucceedsAfterThreeFailures(self):
        """!
        @brief       재시도 함수가 3회 실패 후 성공 시 결과를 반환하는지 검증한다.
        @technique   동등분할, 오류추정
        @case_type   Positive
        @unit        NGV-DD-SW-UNIT-0007
        @requirement NGV-SYS-FR-0012
        """
        attemptCount = 0

        def flakyOperation():
            nonlocal attemptCount
            attemptCount += 1
            if attemptCount < 3:
                raise RuntimeError("fail")
            return "success"

        result = retryOperation(flakyOperation)

        self.assertEqual(result, "success")
        self.assertEqual(attemptCount, 3)
```

- `@brief`: 이 테스트가 검증하는 동작을 한 문장으로 — 이름만으로 부족할 때
  반드시 보완한다.
- `@technique`: 4절의 기법 중 사용한 것(쉼표로 복수 가능).
- `@case_type`: `Positive` 또는 `Negative`.
- `@unit`: 이 테스트가 검증하는 단위 설계 ID([[detailed-design]] 스킬
  `NGV-DD-<레벨>-UNIT-<일련번호>`).
- `@requirement`: 관련 요구사항 ID([[requirements-analysis]] 스킬 ID 체계).

이 네 태그 중 하나라도 빠진 테스트 메서드는 미완성으로 취급하고 보완하세요.
테스트 메서드 이름과 `@brief`가 중복 서술이 되더라도, 이름만으로 검증 대상을
완전히 알 수 없는 경우가 대부분이므로 `@brief`는 생략하지 않습니다.

**명명 규칙(CLAUDE.md)**: 테스트 메서드/변수명도 예외 없이 **3글자 이상,
낙타 표기법(camelCase)**을 사용합니다 — `unittest`의 관용적 `test_snake_case`
대신 `testCamelCase` 형태를 사용하세요(위 예시 참고).

## 6. 흔한 합리화와 위험 신호

| 변명 | 실제 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "구현부터 하고 테스트는 나중에" | 이 프로젝트는 구현 자체가 TDD이므로 정책 위반이다 — Iron Law대로 테스트가 먼저다. |
| "이미 수동으로 확인했다" | 수동 테스트는 기록도, 재실행도 안 되며 압박 속에서 케이스를 빠뜨리기 쉽다. |
| "일단 이번만 예외로" | 그 예외가 누적되어 회귀 방지 장치가 사라진다. |
| "결함 수정을 먼저 하고 테스트는 나중에" | Iron Law 위반 — 재현 테스트 없이는 수정하지 않는다. |
| "기법/케이스유형/Doxygen 태그는 나중에 채우겠다" | 테스트 작성과 동시에 채우지 않으면 결국 누락된다 — 그 자리에서 채운다. |

**위험 신호 — 발견 시 중단하고 다시 시작**: 테스트보다 코드가 먼저 작성됨,
테스트가 처음부터 이유 없이 통과함(뮤테이션 점검 없이), 왜 실패했는지 설명할
수 없음, 기법/케이스유형/Doxygen 태그를 비워둠, 목(mock) 자체를 검증하는
어서션, 명명 규칙(camelCase, 3글자 이상)을 지키지 않은 테스트명.

## 7. ISO 26262 Part 6 / A-SPICE 4.1 정합성

- **ASIL별 커버리지**: 대상 단위의 ASIL 등급에 따라 요구되는 구조 커버리지
  (문장/분기/MC-DC)를 `coverage.py` 등 오픈소스 도구로 측정하고, 테스트
  스위트가 이를 달성하는지 근거를 남깁니다. 미달성 시 어떤 분기/조건이
  빠졌는지 구체적으로 보고합니다.
- **SWE.4/SWE.5/SWE.6 정합**: 단위 검증(SWE.4)은 [[detailed-design]] 스킬
  8절의 검증기준을 근거로 구현(coding) 단계에서, 통합시험(SWE.5)/인수시험
  (SWE.6)은 [[architecture-design]] 스킬 7절의 통합 순서를 근거로 테스트
  단계에서 케이스를 도출합니다.
- **결함 기록/재시험**: 테스트가 결함을 드러내면 결함을 기록하고(SUP.9 연계),
  수정 후 해당 테스트와 회귀 영향을 받는 테스트를 재실행한 증적을 남깁니다.
- **산출물 관리(CL2)**: 테스트 케이스/결과를 식별·버전관리하고, 리뷰 기록을
  남깁니다([[aspice-auditor]] 스킬 PA2.2 기준 참고).

## 8. 추적성(Traceability)

- **ID 체계**: `NGV-TC-<레벨>-<일련번호>` (레벨: `SW`, `HW`, `SYS`)
  - 예: `NGV-TC-SW-0001`
- **양방향 추적**: 요구사항([[requirements-analysis]] ID) ↔ 단위 설계
  ([[detailed-design]] `NGV-DD-...` ID) ↔ 테스트 케이스 ID ↔ 시험 결과 간
  양방향 링크를 확보합니다.
- **추적 매트릭스 갱신**: `docs/traceability/traceability-matrix.md`의
  `시험케이스 ID`/`시험결과` 컬럼을 갱신합니다. 한쪽만 채워진 링크는
  미완성으로 표시합니다.

## 9. 산출 형식

테스트 산출물을 만들 때는 다음을 모두 포함하세요:

1. 테스트 케이스 목록(ID/대상 단위/기법/케이스 유형/Doxygen 설명 유무)
2. RED/GREEN 검증 로그(`python -m unittest` 실행 결과 요약 — 실패 사유, 통과 확인)
3. 발견된 결함과 재현 테스트, 수정 및 재검증 기록(있는 경우)
4. ASIL별 커버리지 근거(`coverage.py` 결과 등)와 미달성 항목(있는 경우)
5. 추적 매트릭스 갱신 내역
6. 구현 단계로 피드백이 필요한 사항(요구사항에는 있으나 미구현된 기능 등)
7. 발견된 미결/트레이드오프 사항 목록(있는 경우 반드시 별도로 보고)
